# 동시성 제어 전략

RailOps에서 가장 중요한 정합성 요구사항은 동일 운행편의 동일 좌석이 중복 예매되지 않는 것입니다.

## 문제 상황

```text
A 사용자와 B 사용자가 동시에 KTX-101, 3호차, 12A 좌석을 선택한다.
둘 다 예매하기를 누른다.
결과는 한 명만 성공해야 한다.
```

허용 결과:

```text
A 성공, B 실패
또는
B 성공, A 실패
```

허용하면 안 되는 결과:

```text
A와 B 모두 HELD 성공
A와 B 모두 RESERVED 성공
```

## 1차 전략: 비관적 락

1차 구현에서는 `ScheduleSeat` 행을 비관적 락으로 잠그는 방식을 우선 사용합니다.

처리 흐름:

```text
1. 요청으로 받은 scheduleSeatIds를 오름차순 정렬한다.
2. 트랜잭션을 시작한다.
3. 해당 ScheduleSeat 행들을 PESSIMISTIC_WRITE로 조회한다.
4. 모든 좌석이 AVAILABLE인지 확인한다.
5. 하나라도 AVAILABLE이 아니면 예외를 발생시키고 롤백한다.
6. 모두 AVAILABLE이면 HELD로 변경한다.
7. Reservation, ReservationSeat, Payment를 생성한다.
8. 커밋한다.
```

장점:

- 동시 요청에서 한 트랜잭션만 좌석을 선점할 수 있어 이해하기 쉽습니다.
- 예매 정합성을 설명하기 좋습니다.
- 좌석 HOLD처럼 충돌 가능성이 높은 쓰기 작업에 적합합니다.

주의점:

- 락 범위를 작게 유지해야 합니다.
- 외부 API 호출이나 오래 걸리는 작업을 락 안에서 수행하면 안 됩니다.
- 여러 좌석을 잠글 때는 항상 같은 순서로 잠가야 데드락 가능성이 줄어듭니다.

## 여러 좌석 선택 시 데드락 방지

나쁜 예:

```text
A 요청: [10, 11]
B 요청: [11, 10]
```

A가 10을 잡고 B가 11을 잡은 뒤 서로 다음 좌석을 기다리면 데드락 가능성이 생깁니다.

해결:

```text
모든 요청의 좌석 ID를 오름차순 정렬한 뒤 잠근다.
A 요청: [10, 11]
B 요청: [10, 11]
```

## 낙관적 락 비교

`ScheduleSeat.version`을 사용해 낙관적 락을 적용할 수 있습니다.

장점:

- 락 대기 시간이 줄어들 수 있습니다.
- 읽기 위주 시스템에서 유리합니다.

단점:

- 충돌 시 재시도 또는 사용자 실패 응답 처리가 필요합니다.
- 좌석 선점처럼 충돌 가능성이 높은 요청에서는 실패 처리 빈도가 높을 수 있습니다.

RailOps에서는 학습 목적으로 비관적 락과 낙관적 락을 비교 문서화하되, 1차 구현은 비관적 락을 우선합니다.

## 유니크 제약 조건의 역할

유니크 제약 조건은 보조 안전장치입니다.

예를 들어 `schedule_seats`에는 다음 제약이 필요합니다.

```text
unique(train_schedule_id, seat_id)
```

이는 동일 운행편에 같은 물리 좌석 상태 행이 중복 생성되는 것을 막습니다.

다만 예매 중복 방지 자체는 좌석 상태 전이와 락으로 처리합니다. `ReservationSeat`만으로 중복 예매를 막으려 하면 PENDING_PAYMENT, EXPIRED, CANCELED 상태를 함께 고려해야 해서 제약 조건이 복잡해질 수 있습니다.

## HOLD 만료와 동시성

만료된 HELD 좌석은 Scheduler가 AVAILABLE로 풀 수 있습니다. 이때 사용자가 동시에 결제 성공을 요청할 수 있으므로 결제 성공 API와 Scheduler 모두 관련 행을 잠그고 상태를 확인해야 합니다.

원칙:

```text
상태 변경은 항상 DB 트랜잭션 안에서 수행한다.
결제 성공과 만료 처리는 같은 좌석을 동시에 변경할 수 있으므로 락 대상이다.
결제 성공 API는 hold_expires_at을 반드시 확인한다.
```

## 테스트 전략

필수 테스트:

- 같은 좌석에 동시 HOLD 요청 시 하나만 성공
- 여러 좌석 동시 HOLD 요청 시 부분 성공 없음
- HELD 좌석에 다른 사용자가 HOLD 요청하면 실패
- 만료된 HELD 좌석 결제 성공 요청 시 실패 및 만료 처리
- Scheduler가 만료 좌석을 AVAILABLE로 복구
- 결제 성공과 Scheduler가 동시에 실행될 때 중복 상태 변경 없음

테스트 도구:

```text
JUnit5
Spring Boot Test
Testcontainers PostgreSQL
ExecutorService 기반 동시 요청 테스트
k6 기반 API 부하 테스트
```
