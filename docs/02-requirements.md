# 요구사항

## 사용자 기능

### 메인 페이지

- 사용자는 서비스 메인 페이지에 접근할 수 있다.
- 메인 페이지에는 열차 검색 진입점이 있어야 한다.
- 로그인 상태에 따라 로그인/회원가입 또는 마이페이지/로그아웃 메뉴를 다르게 표시한다.

### 회원 기능

- 사용자는 이메일, 비밀번호, 이름으로 회원가입할 수 있다.
- 사용자는 이메일과 비밀번호로 로그인할 수 있다.
- 로그인한 사용자는 본인 정보를 조회할 수 있다.
- 로그인한 사용자는 본인 예매 내역을 조회할 수 있다.

### 열차 조회

- 사용자는 출발역, 도착역, 운행일자를 기준으로 열차 운행편을 검색할 수 있다.
- 사용자는 특정 운행편의 상세 정보를 조회할 수 있다.
- 열차 조회 결과는 Redis 캐시 적용 대상이다.

### 좌석 선택

- 사용자는 특정 운행편을 선택한 뒤 객차 목록을 확인할 수 있다.
- 사용자는 객차별 좌석 배치도에서 좌석 상태를 확인할 수 있다.
- 좌석 상태는 AVAILABLE, HELD, RESERVED, BLOCKED로 표시한다.
- 사용자는 AVAILABLE 좌석만 선택할 수 있다.

### 예매와 결제

- 사용자는 선택한 좌석을 예매하기 위해 임시 점유할 수 있다.
- 좌석 임시 점유가 성공하면 Reservation은 PENDING_PAYMENT 상태가 된다.
- Payment는 READY 상태로 생성된다.
- 사용자는 가상 결제 화면에서 성공, 실패, 취소 흐름을 실행할 수 있다.
- 결제 성공 시 예매는 CONFIRMED, 좌석은 RESERVED가 된다.
- 결제 실패, 취소, 만료 시 좌석은 AVAILABLE로 해제된다.

### 예매 취소

- 사용자는 본인 예매만 취소할 수 있다.
- 출발 전 예매만 취소할 수 있다.
- 결제 완료 후 환불 처리는 1차 구현에서는 단순 상태 변경으로 처리하고, 상세 환불 모델은 후순위로 둔다.

## 관리자 기능

- 관리자는 역을 등록, 수정, 삭제, 조회할 수 있다.
- 관리자는 노선을 등록, 수정, 삭제, 조회할 수 있다.
- 관리자는 열차를 등록, 수정, 삭제, 조회할 수 있다.
- 관리자는 운행 편성을 등록, 수정, 취소할 수 있다.
- 관리자는 운행편에 대한 좌석을 생성하거나 상태를 조회할 수 있다.
- 관리자는 특정 좌석을 BLOCKED 상태로 변경할 수 있다.
- 관리자는 BLOCKED 좌석을 AVAILABLE 상태로 해제할 수 있다.
- 관리자는 전체 예매 목록과 예매 상세를 조회할 수 있다.
- 관리자는 운영 로그를 조회할 수 있다.

### 사용자 화면

- 메인 페이지
- 회원가입 페이지
- 로그인 페이지
- 마이페이지
- 열차 검색 페이지
- 열차 상세 페이지
- 객차/좌석 선택 페이지
- 예매 확인 페이지
- 가상 결제 페이지
- 내 예매 목록 페이지
- 예매 상세 페이지

### 관리자 화면

- 관리자 대시보드
- 역 관리 화면
- 노선 관리 화면
- 열차 관리 화면
- 운행 편성 관리 화면
- 좌석 관리 화면
- 전체 예매 조회 화면
- 운영 로그 조회 화면

## 운영 요구사항

- 애플리케이션 로그를 통해 주요 요청과 예외를 확인할 수 있어야 한다.
- 운영 로그 테이블에 예매, 결제, 좌석 차단, 로그인 실패 등의 주요 이벤트를 저장해야 한다.
- Spring Actuator로 애플리케이션 상태를 확인할 수 있어야 한다.
- Prometheus와 Grafana로 주요 지표를 확인할 수 있어야 한다.
- Docker Compose로 로컬과 운영 환경을 재현할 수 있어야 한다.
- AWS EC2 단일 서버에서 Nginx, Spring Boot, PostgreSQL, Redis, Prometheus, Grafana를 실행할 수 있어야 한다.

## 비기능 요구사항

- 동일 좌석에 대한 중복 예매가 발생하면 안 된다.
- 좌석 임시 점유는 만료 시간이 지나면 자동으로 해제되어야 한다.
- 결제 성공 API는 HOLD 만료 여부를 다시 검증해야 한다.
- 관리자 API는 ADMIN 권한 사용자만 접근할 수 있어야 한다.
- 사용자 예매 API는 로그인 사용자만 접근할 수 있어야 한다.
- 조회 API는 필요한 경우 캐시를 적용하되, 예매 정합성을 캐시에 의존하지 않는다.
- 장애 발생 시 원인, 영향, 확인 방법, 복구 절차를 문서화한다.
