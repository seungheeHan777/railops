# 결정 기록

RailOps 프로젝트의 주요 결정과 이유를 기록합니다.

## 2026-07-23: 프로젝트 위치

결정: 프로젝트 루트는 `C:\Users\User\Documents\railops`로 둔다.

이유: 사용자가 Documents 아래에 프로젝트 폴더를 두고 싶다고 결정했으며, 이후 작업 기준 경로를 명확히 하기 위해 별도 `railops` 폴더를 생성했다.

## 2026-07-23: 프로젝트 이름

결정: 프로젝트명은 RailOps로 둔다.

의미: `Rail`은 철도 예매 도메인을, `Ops`는 운영을 뜻한다. 이 프로젝트가 단순 예매 CRUD가 아니라 배포, 로그, 모니터링, 장애 대응까지 포함하는 운영형 백엔드 프로젝트임을 나타낸다.

## 2026-07-23: 초기 구현 순서

결정: 문서 작성과 설계 정리를 먼저 진행하고, 그다음 백엔드/API 구현으로 넘어간다.

이유: 프로젝트 범위가 예매, 결제, 동시성, Redis, 배포, 모니터링까지 넓기 때문에 구현부터 시작하면 설계 결정이 흩어질 가능성이 크다.

## 2026-07-23: HOLD 만료 처리 방향

결정: 1차 설계에서는 PostgreSQL의 `hold_expires_at`을 기준으로 Spring Scheduler가 만료된 HOLD를 정리한다. 결제 성공 API에서도 만료 여부를 재검증한다.

이유: Redis TTL만으로 예매 정합성을 보장하면 Redis 장애나 이벤트 누락 시 문제가 생길 수 있다. DB를 기준으로 두면 정합성을 설명하기 쉽고 장애 상황에서도 복구 기준이 명확하다.

추후 검토: 실제 테이블 구조와 인덱스가 정해진 뒤 Scheduler 쿼리, 실행 주기, 배치 크기, 락 범위를 다시 결정한다.

## 2026-07-23: 프론트엔드 범위

결정: 프론트엔드는 최소 UI로 시작하지만 사용자 화면, 관리자 화면, 메인 페이지를 모두 포함한다.

이유: 백엔드 중심 프로젝트라도 회원가입, 로그인, 좌석 선택, 결제, 관리자 CRUD 흐름을 실제로 확인하려면 화면이 필요하다.
