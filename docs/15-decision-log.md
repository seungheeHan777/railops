# 결정 기록

RailOps 프로젝트의 주요 결정과 이유를 기록합니다.

## 2026-10-18: 기본요금과 예매 취소 구현

결정: 개발 기본요금 50,000원을 설정값으로 두고 새 HOLD부터 가격을 스냅샷으로 저장한다. 출발 전 확정 예매는 전체 좌석에 대해 전액 가상 환불하며 Payment REFUNDED와 환불 금액/시각을 기록한다. 중복 결제/취소는 같은 결과를 반환한다.

이유: 사용자가 직접 결정해야 할 사항이 생기기 전까지 예매 서비스의 전체 흐름을 완성하도록 요청했다. 금액과 환불 정책은 단순하고 변경 가능한 개발 기본값을 선택했다. 실제 운임/수수료와 부분 취소는 별도 정책으로 남긴다.

정합성: 결제/취소/만료는 Payment 행 다음 좌석 ID 오름차순 잠금을 사용한다. 과거 HOLD를 정리할 때 사용자와 만료시각을 함께 확인한다. 만료 응답을 위한 전용 예외에 한해 변경을 커밋한다.

검증: 로컬 PostgreSQL의 별도 스키마 통합 테스트와 데스크톱/모바일 브라우저 흐름을 검증했다. 실제 public 테이블에는 환불 스키마 변경과 DEMO 기준 데이터만 반영했으며 기존 사용자 계정은 변경하지 않았다.

## 2026-10-05: 서비스 완성과 기준 데이터 등록 방식

결정: 현재 구현 범위는 예매 서비스 완성에 집중한다. 역, 노선, 열차, 객차, 좌석, 운행편은 기존 관리자 CRUD로 직접 등록하고 테스트용 데이터로 흐름을 검증한다.

이유: 서비스의 핵심은 좌석 정합성과 HOLD/결제/취소 흐름이며, 실제 운영 데이터 확보를 서비스 완성의 선행 조건으로 두지 않는다.

후속 작업: 단일 기본요금 적용, 본인 예매 목록/상세/취소, 관리자 예매 조회, PostgreSQL 기반 전체 흐름 및 동시성 테스트를 순서대로 진행한다.

## 2026-07-23: 프로젝트 위치

결정: 프로젝트 루트는 `C:\Users\User\Documents\railops`로 둔다.

이유: 사용자가 Documents 아래에 프로젝트 폴더를 두고 싶다고 결정했으며, 이후 작업 기준 경로를 명확히 하기 위해 별도 `railops` 폴더를 생성했다.

## 2026-07-23: 프로젝트 이름

결정: 프로젝트명은 RailOps로 둔다.

의미: `Rail`은 철도 예매 도메인을, `Ops`는 운영을 뜻한다. 이 프로젝트가 단순 예매 CRUD가 아니라 배포, 로그, 모니터링, 장애 대응까지 포함하는 운영형 백엔드 프로젝트임을 나타낸다.

## 2026-07-23: 초기 구현 순서

결정: 문서 작성과 설계 정리를 먼저 진행하고, 그다음 백엔드/API 구현으로 넘어간다.

이유: 프로젝트 범위가 예매, 결제, 동시성, Redis, 배포, 모니터링까지 넓기 때문에 구현부터 시작하면 설계 결정이 흩어질 가능성이 크다.

## 2026-07-23: HOLD 만료 처리 방향

결정: 1차 설계에서는 PostgreSQL의 `hold_expires_at`을 기준으로 Spring Scheduler가 만료된 HOLD를 정리한다. 결제 성공 API에서도 만료 여부를 재검증한다.

이유: Redis TTL만으로 예매 정합성을 보장하면 Redis 장애나 이벤트 누락 시 문제가 생길 수 있다. DB를 기준으로 두면 정합성을 설명하기 쉽고 장애 상황에서도 복구 기준이 명확하다.

추후 검토: 실제 테이블 구조와 인덱스가 정해진 뒤 Scheduler 쿼리, 실행 주기, 배치 크기, 락 범위를 다시 결정한다.

## 2026-07-23: 프론트엔드 범위

결정: 프론트엔드는 최소 UI로 시작하지만 사용자 화면, 관리자 화면, 메인 페이지를 모두 포함한다.

이유: 백엔드 중심 프로젝트라도 회원가입, 로그인, 좌석 선택, 결제, 관리자 CRUD 흐름을 실제로 확인하려면 화면이 필요하다.

## 2026-08-10: 1차 가격 정책

결정: 1차 구현에서는 거리, 노선, 열차 종류, 좌석 타입과 무관하게 모든 좌석 가격을 동일한 단일 기본요금으로 둔다.

이유: 현재 우선순위는 DB 연결, 예매 상태 전이, HOLD/결제/취소 흐름을 안정적으로 완성하는 것이다. 거리별 요금, 노선별 요금, 좌석 타입별 가산금은 가격 정책 테이블이 필요하므로 후순위로 미룬다.

후속 작업: 가격 테이블을 추가할 때는 `base_fares` 또는 `fare_policies`처럼 단일 기본요금을 보관하는 테이블부터 시작한다. 이후 필요하면 Route 기준 가격, SeatType 가산금, TrainSchedule별 override 가격으로 확장한다.
