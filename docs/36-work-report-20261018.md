# 작업 결과와 주의사항

작성일: 2026-10-18

## 완료한 기능

1. 기본요금: 모든 좌석에 개발 기본값 50,000원 적용. `RAILOPS_DEFAULT_SEAT_PRICE`로 변경 가능. 기존 0원 거래는 그대로 보존한다.
2. 사용자 예매: 본인 목록/상세 조회, 상태 필터, 페이지 이동, 결제 재개, 예매 취소.
3. 가상 환불: 확정 예매는 출발 전 전액 환불하고 좌석 반환. Payment REFUNDED 및 환불 금액/시각 기록. 같은 요청을 반복해도 추가 처리하지 않는다.
4. 관리자 예매: 전체 목록/상세 조회, 상태 필터, 회원/결제/환불 정보 확인.
5. 화면: 마이페이지 및 관리자 예매 탭 연결. 작은 화면에서 예매 목록은 세로로 배치한다.
6. 로컬 DB: 환불 컬럼 2개와 결제 상태 제약조건을 변경했다. 기존 회원과 예매 데이터를 삭제하거나 금액을 바꾸지 않았다.
7. 데모 데이터: DEMO_SEOUL → DEMO_BUSAN, DEMO-101, 1호차 8석, 내일/모레 12:00 출발 운행편을 추가했다. 실제 철도 운행 정보가 아니다.

## 함께 수정한 문제

- 만료 처리 후 예외를 던지면 트랜잭션이 롤백되어 만료 기록이 사라지는 문제: HOLD_EXPIRED 전용 예외만 커밋하도록 보완.
- 오래된 HOLD의 실패/취소/만료 처리가 새 점유를 해제할 위험: 점유자와 만료시각을 함께 확인.
- 잠금 순서가 경로별로 달랐던 문제: 결제 행 다음 좌석 ID 오름차순으로 통일. HOLD는 좌석만 같은 순서로 잠금.
- nullable outer join을 포함한 잠금 쿼리의 PostgreSQL 오류 위험: 잠금 대상 좌석 행만 조회.
- 같은 회원이 같은 초에 요청하면 예매/결제 번호가 충돌하는 문제: UUID 번호로 교체.
- 관리자 BLOCK/UNBLOCK이 HELD/RESERVED 좌석을 해제할 위험: AVAILABLE만 BLOCK, BLOCKED만 UNBLOCK 허용.
- 출발 후 신규 HOLD/결제 및 확정 예매 취소 차단. 만료시각과 현재시각이 같은 경계도 만료 처리.
- 상태 필터/페이지 등의 잘못된 API 입력은 400, 동시성 충돌은 409 응답.

## 검증

- 백엔드: PostgreSQL 통합 테스트 10개를 포함한 전체 78개 테스트 통과 (실패/오류/생략 0), bootJar 빌드 통과.
- PostgreSQL 통합 시나리오: 같은 좌석 동시 HOLD, 역순 다중 좌석 요청, 중복 결제/취소, 결제·취소 경합, 만료·결제 경합, 만료 예외 커밋, 같은 회원의 새 HOLD 보호, 권한/페이징/출발 정책, 다중 좌석 부분 실패 롤백, HTTP 회원가입/로그인/예매/환불/ADMIN 접근.
- DB 테스트는 임의의 `railops_test_...` 스키마에서 실행 후 정리한다. 환경변수 없이 실행하는 보통 테스트에서는 PostgreSQL 통합 테스트가 생략된다.
- 프론트: TypeScript/Vite 빌드 및 Playwright 브라우저 검증.
- 브라우저: 1440px 데스크톱과 390px 모바일에서 검색 → HOLD → 마이페이지 결제 → 환불 → 관리자 상세 조회 통과, 페이지 JavaScript 오류 없음.
- UI 검증은 별도 `railops_ui_20261018` 스키마에서 진행하고 검증 계정/데이터와 함께 정리했다. 실제 사용자 계정의 권한/비밀번호를 바꾸지 않았다.

DB 통합 테스트 실행 예시:

```powershell
cd C:\Users\User\Documents\railops\backend
$env:RAILOPS_TEST_DB_URL = 'jdbc:postgresql://localhost:5432/railops'
# 필요하면 RAILOPS_TEST_DB_USERNAME/PASSWORD 설정 (기본값 railops)
.\gradlew.bat test
```

DB 계정에는 테스트 스키마 생성 권한이 필요하다. 실패 시 남은 테스트 스키마는 기존 public 스키마와 구분하여 확인한다.

## 남은 기능

- 예매가 있는 운행편/노선/좌석의 수정·삭제 정책, 운행 취소 시 일괄 환불.
- 회원 정보 수정, 비밀번호 변경, 회원 탈퇴 및 관리자 계정 생성 절차.
- 운영 로그 저장/조회, 인증 실패 응답 통일.
- Flyway, Docker 앱 전체 구성, 배포, 모니터링, 부하 테스트.
- 실제 결제사 연동, 부분 취소, 취소 수수료와 실서비스 요금은 별도 범위.

## 문제와 주의사항

- 현재 결제/환불은 DB 시뮬레이션이다. 실제 돈이 이동하지 않는다. 50,000원과 출발 전 전액 환불은 개발 기본 정책이다.
- 기존 0원 예매는 자동 변경하지 않았다. 새 기본요금은 새 예매부터 적용된다.
- 예매의 금액은 스냅샷이지만 열차명/역명/운행시각은 현재 기준 데이터를 참조한다. 예매가 있는 데이터를 관리자 화면에서 수정하면 과거 예매 표시도 달라질 수 있어 정책 확정 전에는 변경을 피한다.
- 운행편을 CANCELED로 변경해도 기존 확정 예매가 자동 환불되지는 않는다.
- 서버가 꺼져 있으면 Scheduler가 동작하지 않는다. 재시작 후 기본 60초 주기로 최대 100건씩 정리한다. 정리가 지연되어도 결제 API는 만료시각을 재검증한다.
- 부분 취소는 없다. 여러 좌석 예매를 취소하면 전체 좌석이 반환된다. API는 요청당 최대 10석이며 현재 검색 화면은 한 번에 1석씩 HOLD한다.
- 자동화 검증은 기능/경합 검증이지 대규모 부하나 다중 서버 운영 검증은 아니다.
- local의 ddl-auto=update와 개발 기본 DB 비밀번호/JWT secret을 운영에 그대로 사용하지 않는다. 스키마 변경은 별도 SQL 적용 기록을 확인한다.
- 로그아웃은 브라우저 토큰 삭제 중심이다. 발급된 JWT의 서버 측 즉시 폐기와 refresh token은 아직 없다.

이번 작업은 커밋/푸시하지 않았다. 기존 미커밋 문서 변경은 보존했으며 `.idea/`는 작업 대상에서 제외했다.
